# Pure Lean 4 categorical programming architecture

Lojita uses Lean 4.36.0 to parse, elaborate, check and compile both user-owned programs and their contracts. The native host also implements ownership, transport, the store and the session protocol in Lean. The five C relays run external processes or model host devices. A small Lean-to-C interface connects the verified entry to the OS. [Build targets](../lakefile.lean) · [Native host](../runtime/cbits/lean_cli_host.c)

## From a declaration to a sealed module

1. **Syntax.** Lean's parser reads an explicitly named module. The syntactic slice (SynSlice) is represented by `LeanMod` and its `SynUnit`s. A unit carries original UTF-8 source, declared names, a signature slice and syntactic references. Byte positions map back through CRLF normalization. A mutual block stays a single editing unit. Canonical S-expressions preserve the units for storage and plan application. [Source representation](../Lojita/Kernel/LeanCode.lean)
2. **Kernel quotient.** Elaboration adds actual constants, types, bodies and compiler-generated auxiliaries to a checked environment. The **SynSlice ↠ SemGraph** quotient attributes those constants to their owning unit, follows kernel references and records local or external endpoints. The graph distinguishes computational carriers from propositional laws. Definitional equality of signatures and audited axiom footprints feed the gates. A source edit can change spelling while preserving an interface, or reveal a dependency that token matching alone would miss. [Driver](../Lojita/Kernel/Driver.lean) · [Axiom audit](../Lojita/Kernel/AxiomGuard.lean)
3. **Resident import.** The driver imports the public object context once. It caches snapshots by canonical module and dependency snapshot IDs. `ResidentImport` feeds heap-resident `ModuleData` to Lean's importer, retaining the original region lifetimes. Conditional checks can link to a child's staged interface. Publication checks the implementation and its dependency closure. [In-memory import](../Lojita/Kernel/ResidentImport.lean)
4. **Native build.** `compileVerifiedExe` resolves the exact type of a sealed `CliApp` or `ReactiveApp` entry. The host elaborates a small `Main` that applies the appropriate `Lojita.WorldRunner` interpreter. Lean's LCNF emitter produces C from the checked environments. The C toolchain links the objects, Lean runtime, object library and host libraries statically, then renames the completed executable into `bin/candidate`. [Compiler and linker](../Lojita/Kernel/Driver.lean) · [World interpreter](../Lojita/WorldRunner.lean)

## Ownership and the two worlds

`Prog Ψ s t A` describes a computation that changes the owned resource from state `s` to `t` and returns an `A`. A process offers a typed session. A server gives the caller a reply and advances its private state on each request. Stopping it yields the final owned resources. This coalgebraic step is finite under Lean's strict evaluation. The pure evaluator and the IO evaluator interpret the same indexed operations. [Resource calculus](../Lojita/Ownership/Core.lean) · [IO evaluator](../Lojita/Ownership/IO.lean)

A node sees pure `LojitaCtx.*` modules, its contract, its child interfaces and its permitted ancestors. A `WorldProg Δ A` operation contains evidence that its capability occurs in Δ. The pure interpreter threads `SimWorld` through that program. SESSION_ROOT has the additional `Lojita.Session.SessionEnv` probe language. Its indexed scripts run against the reference or built candidate via a terminal, filesystem, network, Git or canvas relay. [Object language](../LojitaCtx/World.lean) · [Probe language](../Lojita/Session/SessionEnv.lean)

## Transport as a two-dimensional virtual equipment

Each stage represents the **whole target program**. Before writing `Gen.<Ti>.<Root>`, SESSION_ROOT uses `LojitaCtx.FuzzGen` in a probe to compare a pure executable specification with the reference on seeded inputs and shrink discrepancies. The closed owner of that root chooses its internal decomposition. [Spec-vs-Ref workflow](../prompts/session-open-world.md)

- **Within a stage, `HomeSt` follows owned imports.** A parent introduces a child by importing its module and assigning a `subspec` to that slot. Each child has one parent. The kernel checks that the parent establishes its contract assuming only the children's abstract interfaces (`stubOf`). The scheduler starts all assigned slots as independent `.workerI` sessions. Sibling count, transition fuel, polling and retry budgets are unbounded. In Reverse-Dialectica, a child’s verified `contradiction` or `countermodel` wakes its immediate parent to revise the current plan. Children whose interfaces, ancestor permissions and lift obligations survive the revision stay in flight. A `liftObstruction` waits for running innocent siblings to finish, then publishes their verified homes in `refs/partial` with the culpable base units in the verdict. [Plan gates](../Lojita/Harness/Core.lean) · [Child lifecycle](../Lojita/Harness/NodeServer.lean)
- **Between stages, `drive-tree` refines an entire ownership tree.** The finite, decidable blueprint starts with empty `baseTrees`. A new refinement names one direct predecessor. A `LiftSpec` maps its root to the new root and routes its owned imports through the third field, the child map. Nested lifts route deeper slots. The upper tree may introduce further children. A root-to-root `TransportSpec` can also supply the required morphism. In the Doc example, T0 owns Label, T1 maps Label, adds Route, and exposes the CLI and its laws for every simulated world. The two trees capture successive descriptions of the same program. [Specification gate](../Lojita/Session/Context.lean) · [Executable Doc example](../prompts/session-open-world.md)

| Direction | Data delivered by the owner | Checked obligation |
| --- | --- | --- |
| Vertical refinement | `LiftSpec`, child routing and a `PortLift` projection | A named square mentions the upper and lower endpoints and proves the required commutation. |
| Horizontal transport | `Plan` moves, child moves and `PortRel` | A relation connects the old and new ports. Poly-transport checks the chosen endpoints and witnesses. Split, merge and preservation of children carry their own obligations. |
| Composition | Operations joined by a shared boundary | `cut₁` wires an output into a downstream operation. `composeTransportsCut` composes relational witnesses for that cut. |

A same-tier replacement can use both directions in one drive. For example, T2b lifts from T1 and transports from T2. A proof square can refer to the pinned source under `Old.*`. A `keep` carries the entire saved subtree while the harness checks its nested lift obligations. Sealing with `(replaces "T2")` retires the old refs and generated directory in the publication journal. In a T0 → T1 → T2 repair, the driver checks old code against its historical base and re-drives successors against the repaired tips. [Kept subtrees](../Lojita/Harness/NodeTransport.lean) · [Tower recovery](../Test/S4Session.lean)

Child routing also determines which base imports a child may use directly. The harness checks local moves, conditional glue, interface satisfaction and the remaining dependency frontier before driving children. [Plan gates](../Lojita/Harness/Core.lean) · [Lift](../Lojita/Transport/Lift.lean) · [Poly-transport](../Lojita/Transport/PolyTransport.lean)

## Resident MCP, publication and replay

On Linux, node MCP routes `check_lean`, `check_agda` and `check_plan` to a resident checker. Each node keeps a warm checker across requests. The MCP process enforces a 120-second wall deadline and samples the checker's RSS against a 1536 MiB budget. Operators can lower these per-worker limits with `LOJITA_CHECK_TIMEOUT_MS` and `LOJITA_CHECK_RSS_MIB`. Linux also enforces a 6 GiB address-space ceiling (including the toolchain's virtual reservations), honoring tighter inherited limits. The supervisor kills and reaps a checker on timeout or excess RSS, records the failure through the normal tool error path, and starts a fresh checker on the next check. The checker disables Linux core dumps, including piped crash handlers, before loading modules. Its launch uses util-linux `setpriv` to tie its lifetime to the supervisor. `read_context` resolves exact module names in the caller's visible catalog. Public library reads return the file text, while tree reads return the canonical source for the frozen module. Node mode filters the checking closure by the owner's allowed ancestors. Session mode resolves the current sealed tips and exposes SessionEnv. The offline acceptance benchmark times six distinct small `check_lean` requests in a warm process and requires a median below 60 ms. Native compilation, cold startup and a full probe have separate costs. [MCP server](../Lojita/MCP/Server.lean) · [Round-trip benchmark](../Test/S4/mcp.py)

The session forks a scratch thread for each proposal and resumes it for mechanical retries. Acceptance advances the owner's durable thread with the semantic outcome. SHA-256 objects store code, interfaces, memories, frozen homes and commits. A journal publishes tree refs and generated Lean source together. For `Gen.T1.Doc.app`, entry preflight and static linking use exactly T1's exported modules and its transitive live predecessor chain. Both building and finishing audit every sealed tree and its generated sources. The build fingerprint covers all sealed tips, so changing even an unrelated tip requires a fresh build and differential replay. The receipt also binds the candidate hash, reference identity and probe hash. [Workspace](../Lojita/Session/Workspace.lean) · [Probe and receipt](../Lojita/Session/Probe.lean) · [Build and finish gates](../Lojita/Session/Runner.lean)

The offline gron replay checks the T0–T3 commit and root-home hashes under opposite sibling schedules. It also exercises a live grandchild refutation, retirement with nine retained modules, and twelve resident Driver workers on recorded drafts. [Replay gate](../test-concurrent-dialectica.sh)
